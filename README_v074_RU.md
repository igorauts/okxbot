# OKX Grid Bot v0.7.4 — универсальный BTC / ETH / SOL

Один движок `okx_bot074.py` для BTC-USDT-SWAP, ETH-USDT-SWAP, SOL-USDT-SWAP, менеджер `okxbot`, независимые экземпляры и отключаемые для каждого экземпляра read-only Burst / Execution Monitor.

## Мастер создания бота

Запрашивает пару, шаг сетки (кратен тику), TP (не меньше maker/maker безубытка +20% от актуальной цены), количество уровней 1–500, размер BUY (минимальный лот и кратность OKX), число базовых BUY LIMIT 1–min(25, уровней сетки), базовых реальных SELL TP 1–25, верхнюю границу (0 = отсутствует; допустимо ниже текущего BID, но вся расчётная сетка должна оставаться положительной) и уникальное имя длиной 3–20 символов.

**Фиксированные правила v0.7.4:** BUY-буфер всегда +5; запрет отмены BUY в пределах 5 шагов сетки от текущего BID; SELL TP-буфер всегда `базовые BUY + 5`, т.е. +6…+30, а максимум реально размещённых TP в штатном режиме — `базовые SELL TP + базовые BUY + 5` (от 7 до 55). BUY и SELL TP базовые цели задаются независимо. Эти три служебных параметра в мастере не вводятся и игнорируются при чтении устаревших настроек прежних версий. У биржи в бурсте могут временно появляться дополнительные прикреплённые TP сверх штатного предела; очистка идёт по одному ордеру, самые удалённые первыми, с сохранением ближайших базовых TP.

Движок сохраняет таймаут и дистанцию обработки частичного BUY (по умолчанию 60 сек и 5 шагов) как внутренние технические настройки; в человекочитаемом меню они скрыты до отдельного решения о пересмотре. Механизм обработки частичных исполнений **не удалён**.

## Менеджер `okxbot`

**«Настройки»** показывает реальную версию исполняемого движка из systemd, а не старый номер схемы `config.json`. Показывает шаг, TP, размер BUY в монетах, `Активные BUY: 25 (макс. 30)` и `Реальные SELL TP: 25 (макс. 55)` для обычной конфигурации. Верхняя/нижняя расчетная граница, примерный капитал 1x и дата создания остаются. Маржа, maker/taker, размер контракта, `LIVE` как отдельная строка и частичные служебные таймеры скрыты. Для старых экземпляров `active_tp_orders=75` больше не показывается как текущая рабочая цель, если движок уже поддерживает `real_tp_target=25`. При несовпадении менеджера с запущенным движком версия и предупреждение выводятся честно.

**«Статус»**: одно понятное состояние вместо дублирования «работает / RUN»; время непрерывной работы службы и аптайм VPS; фактические BUY/SELL TP/виртуальные и частично исполненные ордера из **локального снимка**, и незавершённые агрегированные MARKET. Пропущенные BUY и ошибки наблюдателя — только из *свежей* (не старше 20 секунд) read-only диагностики выбранного экземпляра, иначе «нет данных». Историческое число ордеров, исполненных несколькими сделками, рассчитывается только из полной локальной `fills_v068.sqlite`; это **не равно** количеству когда-либо частично открытых заявок. BID может поступать из свежего лога самого бота, даже если монитор выключен. Никаких прямых запросов на OKX для экрана статуса не делается.

**«Логи (LIVE)» сохраняются** как постоянный живой журнал торговли. Историческая финансовая «Статистика» остаётся отдельным экраном. Мониторы включаются для каждого экземпляра самостоятельно; по умолчанию выключены.

## Публикация и установка

Публикация на GitHub и `install.sh` **НЕ обновляют и НЕ перезапускают** существующие LIVE-экземпляры ETH/SOL: у каждого собственный исполняемый файл и systemd unit. Новый мастер создаёт **новые** экземпляры на v0.7.4 с выключенной торговлей; запуск требует read-only audit и явного подтверждения. Обновление уже работающего бота — отдельная миграция с резервной копией SQLite/WAL, безопасной сверкой ордеров и позиции. Не подменяйте исполняемый файл под живым процессом и не откатывайте мигрированное состояние вслепую.

**Тесты**: `bash run_checks_universal_v074.sh`. 74 исходных регрессионных теста v0.7.3 входят в историю репозитория и продолжают работать против старого файла. Новые v0.7.4 сценарии тестируются отдельно, включая фиксированную защиту, различные базовые цели, миграцию 0.7.3→0.7.4, запрет пользователю редактировать буферы, снимки статуса и обратную совместимость.

## Границы достоверности

Операционный статус читает локальные данные, а не API биржи. Для независимой проверки исполнения ордеров, фактических комиссий, учёта позиции необходим отдельный READ-ONLY аудит OKX. Мониторинг не гарантирует отсутствие ошибок торговли. BTC проверяется офлайн; прежде чем запускать на LIVE, проверьте спецификации конкретного контракта и риски.
