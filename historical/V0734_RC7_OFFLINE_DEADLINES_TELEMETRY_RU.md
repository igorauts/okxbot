# OKX Grid Bot v0.7.34 — OFFLINE RC7: bounded Reader deadlines / quota cancellation / diagnostics

**НЕ ДЛЯ LIVE.** База: исходный финальный архив v0.7.33 пользователя и последующие проверенные RC3–RC6. GitHub Release v0.7.33 остается последним публичным; никаких изменений на VPS или OKX не было.

## Что изменено относительно RC6

1. **Нет phantom quota wait после потери всех клиентов.** Reader запрашивает приоритет у FIFO при каждом проходе. Если все клиенты уже получили timeout, отменили запрос или Reader закрывается, supplier прерывает ожидание (`QuotaRequestAbandoned`), а существующий `PriorityPositionsFIFO` удаляет свой билет через старый queue file. Не расходуем очередной квотный слот на поздний GET, который никому не нужен. Счётчик `quota_abandoned` отдельный от настоящих неисправностей.
2. **Защита от гонки.** Если последний клиент исчез сразу после получения квоты, но до начала HTTP, GET не отправляется; расход слота отдельно виден в `unused_quota_grants`. Абсолютное исключение такой гонки внутри существующего FIFO невозможно без полноценной синхронизации claim/barrier; в коде она ограничена наблюдением и отказом от лишнего HTTP.
3. **Абсолютный IPC timeout 5 секунд.** В `okx_position_reader_client.py` общий монотонный deadline охватывает connect/send/все recv, а не перезапускается на каждом чанке ответа. Медленный или «капельный» Unix-поток не блокирует RUN дольше оговорённого срока до существующего direct GET fallback (его собственное время дополнительно).
4. **Новая диагностика реального Reader-пути.** К существующему per-request `trace_id` добавлены три явных фазы в асинхронный `LatencyJournal`: `position_reader_ipc` (локальное ожидание клиента), `position_reader_quota` (ожидание оригинального общего FIFO), `position_reader_http` (период provider.fetch, включая локальные накладные расходы). Единый `trace_id` позволяет соединить их внутри одного вызова `/positions`. С каждого пакета возвращаются `batch_size`, `quota_wait_ms`, `fetch_ms`. Эти поля допускаются к телеметрии только после безопасной валидации и НИКОГДА не управляют торговлей. Никаких ID ключей API, полных URL или тел HTTP в журнале.
5. **Полный обратный путь прежний.** При выключенном Reader `API.positions()` продолжает индивидуальный GET. При отказе Reader в RUN — прямой GET через тот же account quota; `HARD` и `PANIC` также не зависят от Reader. NET ownership/сверки BUY/SELL, 150мс coalescing, durable intents и стратегия не тронуты.
6. **Негативный стресс:** 10 конкурирующих потоков с приоритетом Emergency и 10 реальных отдельных процессов (4 legacy, 6 priority) используют ОДИН исходный квотный файл, без второго rate limiter. Самые старые неизвестные legacy tickets по-прежнему считаются emergency: строгий приоритет в смешанном режиме не обещается.

## Что проверено

- Полный `bash run_checks.sh`: **PASS, код выхода 0**, включая исходные тесты и 7 новых тестов дедлайна/отмены/телеметрии/10 процессов. Отдельно проверен чисто распакованный релизный ZIP.
- Клиент с drip feed прекращает IPC по общему бюджету, даже если каждая отдельная `recv` бы уложилась в 5 сек.
- После отмены/timed-out запроса исходный FIFO ticket исчезает, существующий резервированный quota counter не меняется, HTTP GET не посылается.
- У пяти одновременных клиентов один GET с индивидуальными NET-срезами и корреляционными метаданными.
- Новые диагностические поля пишутся только в разрешённые фазы и очищаются от неизвестных/чувствительных ключей.
- У `API.positions()` обновлён AST reference **только после review diff относительно RC6**: дополнительно появились исключительно callback метрик, trace/outcome и локальная переменная для неизменного значения возврата; ветки fail-closed/direct GET остаются в исходном виде. Safety AST движка оставлен без изменений.
