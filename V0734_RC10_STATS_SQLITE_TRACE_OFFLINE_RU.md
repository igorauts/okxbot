# v0.7.34 — RC10 OFFLINE: StatsWorker/WAL, reconciler trace и корреляция

**ТОЛЬКО ОФЛАЙН. НЕ УСТАНАВЛИВАТЬ НА LIVE.** Основа — полный проверенный RC9, сам он основан на оригинальном ZIP v0.7.33. Содержимое и tests перепроверяются после упаковки. VPS, реальные API OKX и торговые POST не использовались.

## Подтверждённый исходный конфликт

В RC9 `FillStore.get_rows()` выполнял все SELECT по fills.sqlite под `with self.lock,self._managed_conn()`. Методы записи исполнений используют тот же `self.lock`: значит, фоновая статистика **может блокировать** запись подтверждённых fills в основном процессе на время SELECT/декодирования. Это подтверждено по исходникам, но насколько часто и на сколько миллисекунд происходило в LIVE, пока неизвестно.

## Исправление

- `FillStore.get_rows()` использует отдельное соединение с `mode=ro` и `BEGIN` для согласованного снимка на всю многостраничную выборку (250 ID на SELECT). Python `RLock` писателя при этом **не удерживается**.
- Инициализация БД, WAL, FULL-sync, уникальный PK `(order_id,bill_id)`, проверка неизменяемых fills в `insert()`, `ensure_expected`, сверка фактических количеств/целостности и `trim_verified_fills_for_snapshot` сохранены. Отсутствующий файл БД — ошибка, а не «нет истории». Финансовые формулы и торговые заявки не менялись.
- SQLite WAL допускает одновременное чтение снимка и запись исполнения, что подтверждено тестом с настоящей SQLite и намеренно заблокированным читателем. Второй тест подтверждает, что multi-batch SELECT не принимает fill, добавленный уже после начала снимка. Замеренный результат — **локальная конкурентность**; CPU/IO на боевом VPS отдельно не измерялся.

## Диагностика для следующего причинного анализа

- Точный trace для этапов `pending`, `register_attached`, `track`, `verify_existing`, `positions`, `rest_governor`, `rest_http`, `retry_sleep`, при активном *ранее существовавшем* WS-crossing. Если crossing случился посреди долгого HTTP, на весь старый HTTP он задним числом **не** навешивается.
- `stats_stage` асинхронно пишет локальные интервалы UTC-мс и durations для `capture`, `fills`, `calculation`, `ledger`, `report`, `write` **только после успешно построенной статистики**; ошибки журналирования не могут отменить финансовый снимок. При неполном/ошибочном отчёте интервалы пока не попадают в эту выборку — это ограничение диагностики.
- `tp_to_intent` получил UTC-мс локального WS crossing и durable MARKET-intent (передача в асинхронный журнал после отправки сети, без задержки MARKET). Идентификатор trace — диагностический cohort, не clOrdId и не допуск к торговле.
- `okx_tp_trace_report.py <bot_root>` сопоставляет интервалы StatsWorker и TP; использует ограниченные локальные файлы логов, без REST. Отчёт выдаёт P50/P95 обеих групп с N. **Совпадение интервалов не является доказательством причинности**; отдельно потребуется профилирование ресурсов VPS. Анализ пропусков/ошибочных timestamps не подменяет нулями.

## Какие тесты добавлены

`tests/test_rc10_stats_wal_recon.py`: независимая запись в WAL при остановленном читателе; multi-batch консистентность; отказ при пропавшей DB; отсутствие ретроактивного trace; отказоустойчивость при ошибке диагностического журнала; корректное/некорректное пересечение локальных интервалов. Только реальные временные файлы в `/tmp`, без HTTP и без LIVE.

`run_checks.sh` запускает и новые тесты вслед за исходными регрессиями; инженер обязан посмотреть EXIT-код полного повторного прогона из **чисто распакованного** RC10 ZIP.

## Что НЕ доказано и остаётся блокером перед LIVE

1. Реальное ускорение BID→Collect / BID→Intent на OKX (исторический ориентир ZEC P50 ~2478 мс до этого пакета).
2. Замеры SSD/CPU contention StatsWorker и WAL-файлов на VPS. WAL concurrency не эквивалентна ускорению всех SQLite queries.
3. Отдельная трассировка net fillTime с корректной обработкой рассинхронизации часов; `clOrdId` используется для последующего join без ложных ETA.
4. Mixed-version приоритет PANIC, отказ Reader при systemd restart, полный production install, fail-closed recovery, 24-hour stress, предварительный и последующий GET-only аудит аккаунта.
5. Доказанное преимущество Reader при минимум двух модернизированных ботах; по умолчанию он всё ещё выключен.

Первый в последовательном LIVE rollout — **ZEC**, только после отдельной явной санкции и GET-only аудита. Активные по последнему пользовательскому подтверждению: ZEC/BTC/NEAR/WLD. `rls0733` закрыт PANIC по сообщению пользователя, отдельно не подтверждено GET.
