# OKX Grid Bot v0.7.34 — OFFLINE RC8: смешанный FIFO, приоритет прямого GET и отказоустойчивость

**НЕ УСТАНАВЛИВАТЬ В LIVE.** Это проверяемая исходная сборка для ревью; никаких команд OKX/VPS, торговых POST, системных перезапусков или публикации GitHub не выполнялось. Основа — точный v0.7.33 пользователя + RC7.

## Разбор критического замечания к RC7

Тикеты v0.7.33 не имеют меток. Приоритетный FIFO обязан считать их `EMERGENCY`, поскольку они могли содержать PANIC. При единственном новом ZEC на Reader с тикетом `EXIT`/`NORMAL` это создавало систематическое отставание: ZEC обслуживался после любой старой операции, даже обычной. Дополнительный HTTP/IPC без coalescing только ухудшал задержку. Внешний стенд наблюдал P50 около 990 мс и голодание P95 7.7 с. Это НЕ наши измерения в RC8 и не подмена результата.

## Исправление: две стадии без нарушения общей квоты

1. **MIXED (по умолчанию):** Reader использует `CancellableLegacyFIFO` на том же schema-1 файловом state, lock inode и общем лимите 8/2.1с. Это исходный **FIFO без приоритета**: тикет Reader не помещается всегда после каждого legacy тикета. Он не обгоняет более ранний неопознанный PANIC. Cancellable-обёртка сохраняет уже реализованную отмену ненужного тикета после исчезновения всех клиентов.
2. **FULL-FLEET (позже):** `--quota-scheduling priority --priority-ready-ack ALL_BOTS_PRIORITY_AWARE` включает `PriorityPositionsFIFO` только после внешнего подтверждения, что **все** работающие процессы используют маркированные тикеты. Это ещё НЕ доказанный автоматический детектор версии и НЕ инструкция включать режим на VPS сейчас. Режим по умолчанию остаётся `mixed-fifo`.
3. **Прямые GET нового движка:** при настроенном Reader все индивидуальные `/account/positions` (включая emergency, fallback, отсутствие строки NET) используют ту же исходную квоту с собственным маркированным тикетом: `EMERGENCY` для HARD/PANIC, `EXIT` при подтверждённом локальном WS-hint, иначе `NORMAL`. Supplier переоценивается во время ожидания: полученный PANIC может поднять класс; никакого обхода safety. При отключённом Reader (нет `.env` socket) продолжает действовать исходный `AccountPositionsFIFO.take()`.
4. **Circuit breaker:** после недоступности IPC/непроверенной пустой строки Reader API переключается на индивидуальные GET через общую квоту на 60 секунд. Больше нет повторного полного 5-секундного ожидания на каждом торговом проходе. После истечения срока пробует Reader; успешный вызов сбрасывает breaker. Для HARD/PANIC прямой путь также остаётся доступен. Это fail-safe GET, не торговое разрешение.
5. **Детальная ошибка архивного реестра:** при `retired=true`, но отсутствующем/нечитаемом `state/control_ack.json`, Reader явно сообщает имя и путь и не стартует; торговые движки остаются на своём защищённом прямом GET. Игнорировать такой архив без подтверждённого статуса нельзя.
6. Обновлён AST-reference исключительно для явно изменённого метода `API.positions`, создана новая офлайн-регрессия, поднят SHA `okx_bot.py` в manifest **текущего** engine без изменения движка стратегии. Ни один исторический SHA не изменён. Тесты/сборщик не привязаны к конкретной версии.

## Важная граница результата

Пока только ZEC переведён на Reader, **один GET не объединяется ни с кем**. Даже после устранения голодания Reader может проигрывать прямому GET по IPC и UID-guard. Поэтому безопасная последовательность LIVE после отдельного подтверждения: (1) ZEC на engine v0.7.34 с Reader **выключенным**, проверка всех safety и financial audits; (2) последующие боты по одному с тем же выключенным Reader, со своими аудитами; (3) после допуска минимум 2–4 обновлённых ботов провести отдельный опт-ин Reader в `mixed-fifo`, измеряя реальные quota wait, network, BID→Intent и ошибочные fallback; (4) при доказанном отсутствии старых процессов и успешных PAUSE/HARD/PANIC проверках, отдельно согласовать активацию `priority`. **Никакой одновременной остановки/обновления всех LIVE-ботов.**

В смешанном режиме глобальный PANIC над legacy-тикетами **не гарантируется**, так как невозможно различить обычную позиционную сверку v0.7.33 от PANIC без метки. Гарантировать такое ускорение математически невозможно без миграции всех клиентов (или нового совместимого протокола) и соответствующих испытаний.
