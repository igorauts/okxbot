# OKX Grid Bot v0.7.34 — OFFLINE RC11 (P0: wake storm, mixed FIFO)

Основа: пользовательский опубликованный v0.7.33 и полный исходный OFFLINE RC10.
RC11 содержит два узких исправления для первой поэтапной LIVE-миграции.

## P0-A: нет бесконечного wake при виртуальном TP

Ошибка RC9–RC10: `take_crossed_virtual_stamps()` очищал `_virtual_crossed`, а
`persist_crossed_virtual_tps()` сразу снова вызывал `set_virtual_targets()`.
При всё ещё высоком BID происходило второе «первое» пересечение и новый wake.
В PAUSE/SOFT/неразрешённом групповом EXIT бот мог бесконечно крутить REST.

Решение: `_virtual_woken` живёт отдельно от потребляемых crossing stamps;
повторная публикация неизменной цели при BID >= TP не будит цикл. Латч
сбрасывается ТОЛЬКО (a) при наблюдении BID < TP, (b) если цель удалена,
(c) если изменился TP level. При удалении или перепрайсе старая неиспользованная
crossing stamp также удаляется. Если BID снова пересёк TP снизу, новый wake
допустим. Порядок `wake` перед необязательной телеметрией сохранён.

Ни один MARKET/BUY/SELL/intent/150ms/safety gate не менялся.

## P0-B: прямой GET через исходный FIFO в смешанном парке

Ошибка RC8–RC10: Reader в `mixed-fifo` ждёт равноправно, но собственные прямые
GET (`fallback`, `narrow zero`, обычная ветка при opt-in) получали NORMAL
priority и уступали legacy unlabeled tickets. В RC11 **все** engine-owned
GET используют исходный `AccountPositionsFIFO.take()` по умолчанию.

Новый explicit priority разрешён **только одновременно** при наличии трёх
параметров в конкретном боте:

- `OKX_POSITION_READER_SOCKET` (непустой путь);
- `OKX_POSITION_READER_QUOTA_SCHEDULING=priority`;
- `OKX_POSITION_READER_PRIORITY_ACK=ALL_BOTS_PRIORITY_AWARE`.

Такие параметры НЕЛЬЗЯ устанавливать до окончания обновления всех ботов
аккаунта и отдельной проверки, что сервер Reader также перешёл в priority,
а не mixed-fifo. Во время поэтапного обновления ни один из двух флагов
priority не устанавливать. Нет нового квотного файла/нового лимитера.
Без `OKX_POSITION_READER_SOCKET` код продолжает строго исходный direct GET.

## Офлайн-проверки

- Проверена воспроизводимость исходного бага на RC10: после `take` + повторной
  публикации прежней цели при BID > TP второй wake действительно появляется.
- 250 повторных `take/publish` без retrace в PAUSE, SOFT и RUN-blocked не будят
  заново в RC11.
- Выход BID ниже TP, удаление/добавление TP и изменение цены TP снова корректно
  разрешают новое пересечение; первая crossing stamp сохраняется до потребления.
- Отдельные проверки mixed / incomplete / full priority opt-in.
- Сохранены все прежние регрессии, в том числе single-flight и shared quota.

## Переход к контролируемому LIVE (ПОКА НЕ ИНСТРУКЦИЯ НАЧАТЬ)

1. **RC10 НЕ УСТАНАВЛИВАТЬ**. Новый ZIP RC11 требует нового SHA256 и нового
   staging-каталога; ранее пройденный preflight RC10 не заменяет preflight RC11.
2. Свежая локальная и биржевая GET-only сверка всех четырёх работающих ботов,
   особое внимание ZEC, нулевым/архивным состояниям RLS, pending SELL/BUY,
   виртуальному покрытию, неизвестным POST и PnL/SQLite.
3. Бэкап перед контролируемой установкой. Обновление ZEC первым, с выключенным
   Reader; затем NEAR, WLD, и только последним BTC.
4. Reader включать только после >=2 последовательно обновлённых ботов,
   `mixed-fifo`. Полный priority mode — отдельное согласование после миграции
   всех ботов. Никакого нового UPDATE без наблюдения реального heartbeat/GET
   и безопасного rollback.

LIVE PASS не заявлен; P50 BID→Intent на OKX не измерен.
