# v0.7.38 OFFLINE RC4 — интеграционные fault-injection проверки

**NOT LIVE.** Никаких OKX GET/POST, реального торгового VPS, системных служб или GitHub Release не затрагивалось.

## Зачем RC4

В RC3 существующие unit-тесты подтверждали работоспособность локального ожидания,
но не ловили сообщение `orders` WS, пришедшее во время REST-сверки. На синтетическом
исполнении реального `live_loop` обнаружено: после такого события код мог продолжить
расчёт нового BUY без дополнительного цикла учёта вновь поступившего сообщения.
Это уязвимость согласованности снимка, **не подтверждённый случай дублирования реального ордера**.

## Минимальные исправления

1. После REST, но до новых решений, при накопившемся private WS-событии: повторная
   сверка. PANIC/HARD не блокируются таким событием.
2. Непосредственно перед каждым новым BUY POST: повторная проверка очереди событий.
   При новой записи BUY не выставляем, возвращаемся к полноценной сверке.
3. Если команда PANIC/HARD поступила во время неудачного REST, обратный отсчёт
   трёхсекундного восстановительного backoff сразу прерывается изменением control mode.
4. Финансовые функции place/cancel/TP/PANIC/reconcile не менялись; поменялся только
   цикл `live_loop` (AST RC3 → RC4). `mixed-fifo`, Shared Reader, API quota, TP-буферы,
   схема state и стратегия без изменений.

## Доказательство офлайн

- Исполнение реального AST `live_loop()` с подставными Reader/WS/order действиями,
  без импорта LIVE-конфига или ключей.
- 13 интеграционных сценариев: спокойный рынок; private WS wake; private event в
  REST; private event при расчёте BUY; private/public WS смена поколения во время REST;
  отсутствие здоровья private/public WS; 150 WS-событий подряд; неизвестный исход
  POST (без слепого повтора, пока unresolved); PANIC во время REST; PANIC при outage;
  сравнение аварийного control-mode до/после неудачного REST.
- Предыдущие 15 тестов `okx_idle_reconcile.py` также выполняются.
- Все Reader-модули прежнего регрессионного набора запускаются раздельно, чтобы
  исключить межмодульное влияние async/multiprocess test cleanup.

## Важно до LIVE

- Это детерминированные моковые сценарии и AST-исполнение реальной функции, **не**
  настоящее соединение с OKX и не стресс-тест сетевого оборудования.
- Одного queue.empty() недостаточно для математической атомарности между последней
  проверкой и отправкой POST: безопасность по-прежнему основывается на биржевой
  REST-сверке, durable intents, идентификаторах ордеров и fail-closed обработке
  неизвестного ACK. Не заявляем, что все гонки исключены.
- Требуется отдельное согласование LIVE, установка только на один DOOD с GET-only
  финансовым аудитом, резервной копией и сохранением PIDs остальных процессов.
- Количественный выигрыш по GET и latency в реальном рынке ещё не подтверждён.
